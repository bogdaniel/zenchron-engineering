# Zenchron Engineering Domain Specification v0.1

Status: **Draft**

This document defines the initial domain vocabulary. It intentionally stops short of final JSON Schemas; those schemas must be exercised against representative cases before being frozen.

## Canonical representation

Machine-readable persistent/interchange data is canonical **JSON**.

JSON Schema will describe the public shapes of persisted/interchanged contracts. Go types must preserve the same semantics. YAML is not canonical.

Every durable object should be versioned and designed for deterministic serialization where hashes/signatures become relevant.

## 1. ProjectModel

Answers: **What kind of system is this?**

Initial concerns:

- repository identity and revision;
- architecture and technology stack;
- domains/bounded contexts;
- critical boundaries such as authentication, tenant isolation, payments, personal data;
- repository/path mappings;
- test capabilities;
- deployment/environment characteristics;
- applicable policy profiles;
- known ownership/authority metadata where relevant.

The ProjectModel is project state, not the task itself.

## 2. EngineeringFact

Answers: **What do we currently believe about this work or change, why, and with what certainty?**

Minimum conceptual fields:

```json
{
  "key": "authentication.boundary_modified",
  "value": true,
  "stage": "observed",
  "confidence": "high",
  "subject": {
    "repository": "example/repo",
    "revision": "abc123"
  },
  "provenance": {
    "type": "static_analysis",
    "producer": "example-detector-v1"
  }
}
```

A material fact must support `true`, `false`, or `unknown` semantics where appropriate.

Stages may include:

- `predicted`;
- `observed`;
- `verified`.

Policy must be able to distinguish provenance/confidence classes when required.

## 3. EngineeringPolicy

Answers: **When engineering facts match these conditions, what must be required or prohibited?**

Example conceptual rule:

```json
{
  "id": "AUTH-BOUNDARY-001",
  "when": {
    "fact": "authentication.boundary_modified",
    "equals": true
  },
  "require": {
    "obligations": [
      "threat_model",
      "auth_regression_tests",
      "independent_security_review"
    ]
  },
  "authority": {
    "git.merge": {
      "human_approval": "required"
    }
  }
}
```

Policy resolution after facts are established should be deterministic wherever practical.

## 4. EngineeringWorkContract

Answers: **What is required and permitted for this specific unit of engineering work?**

Initial sections:

- metadata and revision;
- normalized intent/objective;
- acceptance intent;
- predicted/known scope;
- relevant engineering facts;
- invariants;
- obligations;
- required claims/evidence classes;
- permissions and explicit prohibitions;
- authority conditions by protected action;
- context requirements;
- budget constraints where applicable;
- permitted execution-provider classes;
- provenance: project revision, policy revision/set, compiler version.

The contract describes required outcomes, not a rigid sequence of named agents.

### Invariants versus obligations

An invariant describes a property that must remain true, for example:

```json
{
  "id": "TENANT-001",
  "statement": "tenant isolation must not weaken"
}
```

An obligation describes engineering work/evidence required to establish or protect outcomes, for example `tenant_authorization_tests` or `independent_security_review`.

## 5. EvidenceBundle

Answers: **What was actually established, by whom, about which exact subject?**

Evidence should preserve separation between claims and supporting evidence.

Minimum concerns:

- bundle identity/version;
- subject repository/tree/commit;
- contract revision;
- applicable policy revision/set;
- claim identifier/type;
- evidence producer identity/type;
- environment/toolchain where relevant;
- result;
- provenance/integrity metadata;
- lifecycle state (`valid`, `stale`, `invalid`, etc.).

A changed subject defaults dependent evidence to stale unless explicit analysis establishes continued applicability.

Humans may be evidence/approval producers with identity/role metadata; they are not modeled merely as an escape hatch.

## 6. AuthorityDecision

Answers: **May this specific protected action happen now?**

Authority is action-scoped.

Conceptual form:

```json
{
  "action": {
    "type": "git.merge",
    "target": "main"
  },
  "status": "awaiting_authority",
  "satisfied": [
    "tests",
    "sentinel_assurance"
  ],
  "missing": [
    "human_approval:security-owner"
  ]
}
```

Initial statuses:

- `incomplete`;
- `blocked`;
- `stale`;
- `awaiting_authority`;
- `authorized`.

## Capability, permission, authority

These are deliberately distinct:

- **Capability**: the runtime technically can perform an operation.
- **Permission**: the actor/contract is allowed to attempt it.
- **Authority**: this particular protected action may occur now given current state and evidence.

Executable action is constrained by their intersection.

## Contract lifecycle

A contract is revisioned.

During execution:

1. observe the actual change;
2. derive new/changed facts;
3. compare them with the existing governance envelope;
4. if material impact expands, suspend affected privileged actions;
5. resolve policy again;
6. create a new contract revision;
7. mark no-longer-applicable evidence stale;
8. continue under the revised contract.

Recompilation may automatically increase obligations. It may not automatically grant sensitive privilege.

## v0.1 evaluation cases

The schemas and evaluator must be tested against at least these classes:

1. trivial copy/docs/UI change;
2. normal behavioral/API/business-rule change;
3. authentication/session/data-sensitive change;
4. hidden scope expansion from ordinary to sensitive;
5. material uncertainty or initial misclassification;
6. evidence made stale by a subsequent change;
7. execution requesting additional privilege;
8. failing assurance followed by remediation.

## Open design questions

The first implementation issues should resolve through tests rather than speculation:

- exact fact value model and confidence vocabulary;
- policy expression language versus a deliberately small v0.1 rule model;
- canonical hashing/version semantics;
- evidence dependency/staleness granularity;
- minimum ProjectModel needed for useful classification;
- which authority decisions can be deterministic in v0.1;
- how much execution planning should remain ephemeral.
