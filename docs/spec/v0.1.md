# Zenchron Engineering Domain Specification v0.1

Status: **Implemented contract draft**

This document defines the fixture-tested v0.1 domain vocabulary. The six schemas under `schemas/` are the normative external contracts; this specification explains their semantics and deliberate limits.

## Canonical representation

Machine-readable persistent/interchange data is canonical **JSON**.

JSON Schema Draft 2020-12 describes the public shapes of persisted/interchanged contracts. Go types must preserve the same semantics. YAML is not canonical.

Every durable object requires `schema_version: "0.1"` and an identity. Aggregate contracts also carry an opaque revision string; v0.1 facts are immutable records bound to an exact subject revision instead of independently revisioned aggregates. Every schema has an explicit URI `$id` and rejects undeclared object properties. Canonical hashing/signing rules are not defined in v0.1.

### Collection identity and ordering

Collections whose members have durable identities and are referenced or updated by identifier use JSON objects keyed by that identifier. The key is the member identity; the value does not repeat an `id` field. This applies to policy rules, ProjectModel boundaries and test capabilities, policy/contract invariants and obligations, contract required claims, and evidence items. JSON object member names are unique, so two definitions cannot claim the same identity.

Arrays are reserved for non-addressed values, references, or composite values such as paths, fact identifiers, actions, and authority conditions. Duplicate values are rejected where they have no meaning. No array ordering has semantic meaning in v0.1; a future ordered contract must state that explicitly.

### Go representation and serialization

The `domain` package preserves each identity-addressed collection as a Go map keyed by the external identifier. `FactValue` is a closed Go value whose states encode as JSON `true`, `false`, or `"unknown"`; its zero value is invalid, so absence cannot collapse into false.

Canonical ingestion has one path: strict JSON decoding, conversion to the typed v0.1 representation, then validation against the normative JSON Schema. Strict decoding rejects duplicate object member names at every nesting level and rejects any non-whitespace content after the single top-level JSON value.

Go's `encoding/json` sorts map keys when encoding, so the same v0.1 Go value has deterministic compact output within this implementation. JSON object order remains semantically irrelevant. These bytes are not yet a cryptographic canonicalization format: consumers must not assume cross-language or long-term byte identity for hashes or signatures. Canonical hashing, string normalization, and signature rules remain deferred.

## 1. ProjectModel

Answers: **What kind of system is this?**

The tested v0.1 contract requires identity, model revision, and an exact repository/revision subject. It may describe:

- repository identity and revision;
- critical boundaries such as authentication, tenant isolation, payments, personal data;
- test capabilities;
- applicable policy profiles.

Architecture inventories, deployment metadata, ownership, and general path mappings remain deferred until a fixture needs them. The ProjectModel is project state, not the task itself.

The initial fact-analysis implementation loads ProjectModel snapshots through the strict canonical JSON boundary. Its deterministic critical-boundary detector compares normalized predicted or observed paths with the model's boundary paths. A known path set produces a high-confidence Boolean fact for each configured boundary type; unavailable path information produces a low-confidence `"unknown"` fact rather than an assumed negative. Predicted facts bind exactly to the ProjectModel subject and use `intent_analysis` provenance, while observed facts may bind to a later candidate revision in the same repository and use `path_analysis` provenance. Detector provenance identifies the deterministic producer, and the resulting fact set is keyed by durable fact identity for policy evaluation.

Boundary paths in v0.1 are exact repository-relative paths or directory-prefix patterns ending in `/**`. A richer general glob language is deferred until representative project models require it.

## 2. EngineeringFact

Answers: **What do we currently believe about this work or change, why, and with what certainty?**

Required fields:

```json
{
  "schema_version": "0.1",
  "id": "fact-auth-1",
  "key": "authentication.boundary_modified",
  "value": true,
  "stage": "observed",
  "confidence": "high",
  "subject": {
    "repository": "example/repo",
    "revision": "abc123"
  },
  "provenance": {
    "type": "static_analysis",
    "producer": "example-detector-v1"
  }
}
```

A v0.1 fact value is `true`, `false`, or the string `"unknown"`. `null`, absence, and ad hoc values such as `"maybe"` are invalid. The initial evaluation corpus only needs Boolean material assertions, so other typed values are deferred rather than speculatively generalized.

Stages may include:

- `predicted`;
- `observed`;
- `verified`.

Confidence is `low`, `medium`, or `high`. Provenance requires a producer and producer-defined type. Policy may distinguish provenance/confidence classes when later evaluator work requires it.

## 3. EngineeringPolicy

Answers: **When engineering facts match these conditions, what must be required or prohibited?**

An `EngineeringPolicy` is a revisioned set of rules. Each v0.1 rule has one fact-equality predicate: `when.fact` equal to `true`, `false`, or `"unknown"`. A predicate may also constrain fact stage, confidence, provenance type, or producer. Its `effect` contains one or more of obligations, invariants, permissions, prohibitions, or action-scoped authority conditions.

Example rule:

```json
{
  "AUTH-BOUNDARY-001": {
    "when": {
      "fact": "authentication.boundary_modified",
      "equals": true
    },
  "effect": {
    "required_claims": {
      "claim-auth-regression-tests": {
        "evidence_class": "test_result",
        "independent_from_change_producer": true
      },
      "claim-security-owner-approval": {
        "evidence_class": "human_approval",
        "independent_from_change_producer": true
      }
    },
      "obligations": {
        "auth-regression-tests": {
          "statement": "Authentication regression tests must pass.",
          "required_claims": ["claim-auth-regression-tests"]
        }
      },
      "authority_conditions": [
        {
          "action": { "type": "git.merge", "target": "main" },
          "required_claims": ["claim-auth-regression-tests", "claim-security-owner-approval"]
        }
      ]
    }
  }
}
```

Policy effects define required claims, including their evidence class and independence requirement. Obligations and authority conditions reference those claim identifiers. Human approvals are required claims with an evidence class such as `human_approval`; they are not a separate `required_authorities` mechanism. A typed human producer supplies the corresponding evidence.

No Boolean expression language or ordering semantics is defined by the schema. The v0.1 compiler evaluates matching rules deterministically and rejects conflicting requirement definitions, required-claim definitions, authority conditions, and permission/prohibition pairs rather than applying implicit rule ordering.

## 4. EngineeringWorkContract

Answers: **What is required and permitted for this specific unit of engineering work?**

Required sections:

- schema version, identity, revision, and exact repository/revision subject;
- normalized objective;
- acceptance intent;
- scope stage plus allowed and prohibited paths;
- identifiers of relevant engineering facts;
- invariants;
- obligations;
- required claims/evidence classes;
- permissions and explicit prohibitions;
- authority conditions by protected action;
- provenance: ProjectModel revision, policy revision, compiler version, and previous contract revision when recompiled.

Required claims are keyed by claim identifier and identify an evidence class plus whether evidence must be independent from the change producer. The contract describes required outcomes, not a rigid sequence of named agents. Context requirements, budgets, and execution-provider classes remain deferred until representative fixtures require durable contract fields for them.

### Invariants versus obligations

An invariant is keyed by its identifier and describes a property that must remain true, for example:

```json
{
  "TENANT-001": {
    "statement": "tenant isolation must not weaken"
  }
}
```

An obligation describes engineering work/evidence required to establish or protect outcomes, for example `tenant_authorization_tests` or `independent_security_review`.

## 5. EvidenceBundle

Answers: **What was actually established, by whom, about which exact subject?**

Evidence preserves separation between claims and supporting evidence. A bundle binds every contained evidence item to one exact subject, contract revision, and policy revision. Evidence from different subject revisions belongs in separate bundles.

Minimum concerns:

- bundle identity/version;
- subject repository/tree/commit;
- contract revision;
- applicable policy revision/set;
- claim identifier;
- evidence class, explicitly recorded on supporting evidence and compared with the contract's required claim class; it is not inferred from producer type, environment, or provenance;
- evidence producer identity/type;
- environment/context for every evidence item, plus toolchain where relevant;
- result (`pass`, `fail`, or `inconclusive`);
- provenance/integrity metadata;
- lifecycle state (`valid`, `stale`, `invalid`, or `incomplete`).

Result and lifecycle are independent: a valid failing test result is applicable evidence establishing failure, while a stale passing result cannot satisfy a current claim. Non-valid lifecycle states require a reason. A changed subject defaults dependent evidence to stale unless explicit analysis establishes continued applicability.

### Lifecycle operations

The v0.1 `evidence.HasApplicablePassingEvidence` function makes applicability explicit. It returns true only when a passing `valid` item has the requested claim identifier and evidence class in a bundle whose subject, contract revision, and policy revision exactly match the requested binding. Stale, invalid, incomplete, failing, and inconclusive items are not applicable. A true result establishes only that applicable passing evidence exists; it does not establish independence from the change producer, final claim satisfaction for authority, permission, or action authority. Those decisions require the change-producer identity and action context and remain evaluator work.

When a subject, contract revision, or policy revision changes, a new revision of the existing bundle may mark its valid items stale while retaining the bundle's original binding. Old evidence must never be silently rebound to the new target. v0.1 does not model the dependency analysis needed to carry evidence forward, so fresh evidence is required after a binding change.

Producer types are `execution_provider`, `assurance_provider`, `deterministic_tool`, and `human`. Producer-specific payloads do not enter the core shape. Every evidence item requires a generic `environment` with a type and identifier. This context can identify a CI run, local tool execution, assurance service invocation, code-review record, or control-plane approval without provider-specific fields. Toolchain and integrity metadata remain optional.

## 6. AuthorityDecision

Answers: **May this specific protected action happen now?**

Authority is action-scoped.

Required form includes the protected action, exact subject and contract revision, exact evidence basis, current runtime capability, current contract permission, decision status, and explanatory requirement sets:

```json
{
  "schema_version": "0.1",
  "id": "decision-auth-merge",
  "revision": "1",
  "subject": {
    "repository": "example/repo",
    "revision": "abc123"
  },
  "contract": {
    "id": "contract-auth-session",
    "revision": "1"
  },
  "basis": {
    "change_producer": {
      "id": "change-executor",
      "type": "execution_provider"
    },
    "evidence_bundles": {
      "evidence-auth-review": { "revision": "1" }
    }
  },
  "action": {
    "type": "git.merge",
    "target": "main"
  },
  "capability": { "status": "available" },
  "permission": { "status": "granted" },
  "status": "awaiting_authority",
  "satisfied": ["claim-auth-regression-tests"],
  "missing": ["claim-security-owner-approval"],
  "stale": [],
  "blocking": []
}
```

Initial statuses:

- `incomplete`;
- `blocked`;
- `stale`;
- `awaiting_authority`;
- `authorized`.

Schema invariants reject `authorized` unless capability is available, permission is granted, and missing/stale/blocking sets are empty. `incomplete`, `stale`, `blocked`, and `awaiting_authority` require a corresponding explanatory set to be non-empty. These are structural safeguards, not a substitute for the evaluator in issue #7.

`basis.change_producer` records the exact typed identity that produced the change under evaluation. This is durable decision input because a claim requiring independence can be satisfied or missing depending on that identity. `basis.evidence_bundles` is an identifier-keyed object whose values contain exact bundle revisions. It records the complete evidence input set considered by the evaluator and may be empty when no evidence exists yet. Bundle identifiers cannot appear twice with conflicting revisions. The evaluator in issue #7 owns cross-object checks and decision computation; v0.1 defines the durable reproducibility inputs.

### Deterministic evaluator

The v0.1 `authority.Evaluate` function constructs a decision from an explicit work contract, protected action, runtime-capability snapshot, change-producer identity, and identifier-keyed evidence-bundle set. It records the exact typed change producer plus every supplied bundle identity and revision in the decision basis. A bundle can satisfy a claim only when its subject, contract, and policy bindings exactly match the contract; an item must also have the claim's expected evidence class, a `valid` lifecycle, and a passing result. Claims marked `independent_from_change_producer` are not satisfied by an item produced by the change producer.

Valid failing evidence for a required claim is `blocked`. Before binding, lifecycle, or result semantics are considered, a `human_approval` item is eligible only when its producer has type `human`; a non-human item of that evidence class is missing approval, not authority, whether it reports pass or fail. A valid applicable failing human approval is an explicit rejection and is `blocked`. Evidence for a required claim with a stale lifecycle or a mismatched binding is `stale` unless applicable valid evidence satisfies that claim. Absent, incomplete, invalid, inconclusive, wrong-class, producer-dependent, or non-human human-approval evidence is `missing`. A denied contract permission or unavailable runtime capability is also `blocked`; unknown capability is `incomplete`. With no blocking or stale requirements, a decision with only missing `human_approval` claims is `awaiting_authority`; other missing requirements are `incomplete`; otherwise it is `authorized`. The evaluator applies no provider-specific rule and makes no LLM call.

## Capability, permission, authority

These are deliberately distinct:

- **Capability**: the runtime technically can perform an operation.
- **Permission**: the actor/contract is allowed to attempt it.
- **Authority**: this particular protected action may occur now given current state and evidence.

Executable action is constrained by their intersection.

## Contract lifecycle

A contract is revisioned.

During execution:

1. observe the actual change;
2. derive new/changed facts;
3. compare them with the existing governance envelope;
4. if material impact expands, suspend affected privileged actions;
5. resolve policy again;
6. create a new contract revision;
7. mark no-longer-applicable evidence stale;
8. continue under the revised contract.

Recompilation may automatically increase obligations. It may not automatically grant sensitive privilege.

### Observed-scope reassessment

The v0.1 reassessment service derives observed facts from the candidate
change, compares the changed paths and resulting policy outcomes with the
current contract, and recompiles only when an observed deviation is material.
Paths outside the allowed scope, prohibited paths, unavailable observed path
information, and semantic changes to the contract outcomes are material
deviations. Semantic comparison is deterministic and order-independent: it
detects additions, removals, and changed definitions of invariants,
obligations, required claims, permissions, prohibitions, and authority
conditions. Thus a same-ID requirement with a changed statement or evidence
requirement is material, as is a permission that no longer resolves. A
material reassessment returns the next contract revision and suspends every
protected action governed by the old or new contract until the revised
contract is evaluated.

The subject is an exact contract and evidence binding. Within the same
repository, an observed subject revision different from the current contract's
revision is therefore a material `subject_revision_changed` deviation even
when paths and resolved governance outcomes are otherwise unchanged. It
returns the requested next contract revision bound to that observed subject,
without adding obligations solely because the revision changed. An identical
subject revision alone is not material; a repository change remains invalid.

Recompilation may introduce additional obligations automatically. Reassessment
must use the same ProjectModel and EngineeringPolicy identity/revision recorded
in the current contract provenance; governance evolution is a separately
authorized transition. If observed policy resolution requests a permission
outside the current contract, reassessment remains material and returns that
permission as a structured requested privilege expansion. The revised contract
retains the existing permission ceiling and the affected actions remain
suspended; reassessment neither grants the permission nor terminates as a
generic compiler failure. Permission or obligation removal is not a privilege
expansion, but remains material because the prior authority envelope cannot
continue unchanged. An observed path matching a current prohibited path remains
prohibited and is never copied into allowed scope; non-prohibited discovered
paths may be incorporated after reassessment. Evidence bundles bound to the
prior contract are revised with valid items marked stale; v0.1 has no dependency
model that can prove carry-forward applicability, so it requires fresh evidence
for the new binding.

Observed-scope reassessment is not a contract-editing API. The current
contract's objective, acceptance intent, and prohibited-path baseline are
authoritative. Callers must supply an equivalent objective and
order-independent acceptance intent or reassessment fails deterministically;
they may omit prohibited paths or supply only an equivalent baseline. New or
changed prohibited paths are rejected as governance evolution rather than
merged into the observed contract. Current allowed paths are retained, while
legitimate observed non-prohibited paths may expand the observed allowed scope.

## v0.1 evaluation cases

The schemas and evaluator must be tested against at least these classes:

1. trivial copy/docs/UI change;
2. normal behavioral/API/business-rule change;
3. authentication/session/data-sensitive change;
4. hidden scope expansion from ordinary to sensitive;
5. material uncertainty or initial misclassification;
6. evidence made stale by a subsequent change;
7. execution requesting additional privilege;
8. failing assurance followed by remediation.

## Fixture findings and deferred questions

Representative fixtures changed or narrowed assumptions from the prose draft:

- Facts use a closed Boolean/`"unknown"` value model and a closed three-level confidence vocabulary. General fact values are deferred.
- Policy uses one fact-equality predicate per rule with optional stage, confidence, and provenance qualifiers. A general expression language is unnecessary for the initial corpus.
- Obligations and required claims are separate. Claims carry evidence-class and producer-independence requirements.
- Identity-addressed collections use identifier-keyed objects; array item equality could not guarantee unique member IDs.
- Evidence result and lifecycle must be separate; a failing result can be current and valid.
- Every evidence item requires generic environment/context binding, including human evidence, preserving P7.
- Bundle-level binding deliberately prevents mixing evidence from different subject, contract, or policy revisions. Dependency-level carry-forward remains evaluator work.
- Scope expansion can add facts, obligations, and claims while leaving permissions unchanged; the fixture does not encode an automatic privilege grant.
- Authority decisions need explicit capability and permission snapshots plus an exact EvidenceBundle basis for P10 replay.
- Fixed agent-role workflows are rejected by closed policy and contract schemas.

Still deferred:

- canonical serialization, hashing, and signature semantics;
- evidence dependency analysis finer than bundle subject binding;
- budget, context, provider-class, and richer ProjectModel fields;
- durable execution-planning state.
